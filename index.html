Introduction

Why Clean Code Matters

You are a programmer. You want to be a better one. Good — we need better programmers.

This is a book about good programming. Not about how to program — you already know that. It is about how to write code that other human beings can read, understand, and maintain. Code that will still make sense six months from now, when the original author has moved on and the requirements have shifted.

The book has three parts. Part One lays out the principles, patterns, and practices of writing clean code: how to name things, how to write functions, how (and whether) to comment, how to format code, how to tell objects from data structures, how to handle errors, how to draw boundaries around third-party code, how to write tests, how to organise classes, how to build systems, how to let good design emerge, and how to write concurrent code that does not betray you.

Part Two is a set of case studies of ever-increasing complexity: a command-line argument parser, the comparison compactor from JUnit, and a date library called SerialDate. These are not toy examples — they are real code, cleaned up step by step.

Part Three is the payoff: a single chapter listing all the smells and heuristics gathered along the way, a knowledge base for thinking about code.

Every chapter follows the same shape. A short story introduces the ideas. A box of Key Ideas distils the takeaways. And three Try It Yourself questions invite you to test the ideas against your own code.

You do not need to agree with everything here. The book is opinionated, sometimes stridently so. But the opinions are grounded in decades of practice, and they are offered as a starting point for your own professional judgement.

Remember: code is read far more often than it is written. Write for the reader.

Key Ideas

  • Clean code is code that is easy to read, understand, and change.
  • The book has three parts: principles and practices, case studies, and a catalogue of smells and heuristics.
  • Every chapter has a story, key ideas, a code example, and three exercises.
  • Code is read far more often than it is written.

Try It Yourself

  1. Look at the last function you wrote. Would a stranger understand it without asking you?
  2. Which of the book's three parts are you most curious about?
  3. What does "clean" mean to you, before you've read the book?

Clean Code

There will always be code — so we may as well write it well

Some people argue that code is on its way out — that models and requirements will replace it, that business people will generate programs from specifications, that programmers simply won't be needed. This is nonsense. Code is the language in which we express requirements. At some level those details cannot be ignored or abstracted; they have to be specified. And specifying requirements in such detail that a machine can execute them is programming.

We have all seen what happens when code goes bad. A company writes a killer app, rushes it to market, and makes a huge mess in the code. As they add feature after feature, the code gets worse and worse until they cannot manage it any longer. The company goes out of business. It was the bad code that brought the company down. LeBlanc's law says it all: Later equals never.

The total cost of owning a mess is enormous. As the mess builds, team productivity asymptotically approaches zero. Management adds more staff, but the new staff don't understand the design, and they make more messes. Eventually the team rebels and demands a grand redesign in the sky — a tiger team starts over from scratch, and the race between the old and new systems can take a decade.

The fault is not in our stars but in ourselves. Managers and marketers look to us for the information they need. It is our job to defend the code with as much passion as they defend the schedule. A doctor would refuse to operate without washing his hands, even if the patient demanded it. So too a programmer must refuse to make a mess, even when the deadline is tight.

So what is clean code? Bjarne Stroustrup says it is elegant and efficient, with straightforward logic and minimal dependencies. Grady Booch says it reads like well-written prose. "Big" Dave Thomas says it can be read and enhanced by someone other than its author, and that it has unit tests. Michael Feathers says it always looks like it was written by someone who cares. Ward Cunningham says you know you are working on clean code when each routine turns out to be pretty much what you expected.

Whatever definition you prefer, one thing is clear: a programmer who writes clean code is an artist who can take a blank screen through a series of transformations until it is an elegantly coded system. And the first rule of the craft is simple: leave the campground cleaner than you found it.

// Bad: what does this function do?
public List<int[]> getThem() {
  List<int[]> list1 = new ArrayList<int>();
  for (int[] x : theList)
    if (x[0] == 4)
      list1.add(x);
  return list1;
}

// Good: revealing intent through names
public List<Cell> getFlaggedCells() {
  List<Cell> flaggedCells = new ArrayList<Cell>();
  for (Cell cell : gameBoard)
    if (cell.isFlagged())
      flaggedCells.add(cell);
  return flaggedCells;
}

The simplicity of the code has not changed — same number of operators, same number of nesting levels. But the code has become explicit. That is the power of choosing good names.

Key Ideas

  • Code is the language in which we express requirements — it will never disappear.
  • Bad code brings down companies; the cost of owning a mess is enormous.
  • You won't make the deadline by making a mess — the only way to go fast is to keep the code clean.
  • Clean code is focused: each function, class, and module does one thing well.
  • The Boy Scout Rule: leave the campground cleaner than you found it.

Try It Yourself

  1. Find a function you wrote in the last week. Can you tell what it does from its name alone?
  2. Which of the definitions of clean code (Stroustrup, Booch, Thomas, Feathers, Cunningham) resonates most with you? Why?
  3. Apply the Boy Scout Rule: make one small improvement to code you are about to commit.

Meaningful Names

A name should tell you why it exists, what it does, and how it is used

Names are everywhere in software. We name variables, functions, arguments, classes, packages, source files, directories. We name and name and name. Because we do so much of it, we had better do it well.

The name of a variable, function, or class should answer all the big questions. It should tell you why it exists, what it does, and how it is used. If a name requires a comment, then the name does not reveal its intent. Compare int d; // elapsed time in days with int elapsedTimeInDays; — the second needs no comment and cannot be misunderstood.

Avoid disinformation. Do not call a grouping of accounts an accountList unless it really is a List. Beware of names that vary in small ways: XYZControllerForEfficientHandlingOfStrings and XYZControllerForEfficientStorageOfStrings look alike and are impossible to tell apart. Avoid lower-case l and upper-case O as variable names — they look like 1 and 0.

Make meaningful distinctions. Number-series naming (a1, a2, a3) is the opposite of intentional naming. Noise words are another meaningless distinction — ProductInfo and ProductData are not different from Product in any meaningful way. If names must be different, they should also mean something different.

Use pronounceable names, because programming is a social activity — if you cannot pronounce it, you cannot discuss it without sounding like an idiot. Use searchable names: single-letter names and numeric constants are hard to locate across a body of text. Length of a name should correspond to the size of its scope — very short names for tiny scopes, longer names for bigger ones.

Avoid encodings. Hungarian notation and m_ member prefixes are remnants of older languages and environments. Modern IDEs and type systems make them unnecessary, and they clutter the code. Class names should be nouns; method names should be verbs. Pick one word per concept and stick with it. Don't be cute. Don't pun. Use solution domain names when you are writing about the solution, and problem domain names when you are writing about the problem. Add context — but not gratuitous context.

// Bad: noninformative, noise words, encodings
class DtaRcrd102 {
  private Date genymdhms;
  private Date modymdhms;
  private final String pszqint = "102";
}

// Good: intention-revealing, pronounceable, searchable
class Customer {
  private Date generationTimestamp;
  private Date modificationTimestamp;
  private final String recordId = "102";
}

Intelligent conversation is now possible: "Hey, Mikey, take a look at this record! The generation timestamp is set to tomorrow's date! How can that be?"

Key Ideas

  • Names should reveal intent; if a name needs a comment, the name has failed.
  • Avoid disinformation, noise words, encodings, and number-series naming.
  • Use pronounceable, searchable names — the length of a name should match its scope.
  • Class names are nouns; method names are verbs; pick one word per concept.
  • Add meaningful context, but not gratuitous context.

Try It Yourself

  1. Rename three variables in a recent program so that they reveal intent.
  2. Find a Manager or Processor class and describe its responsibility in 25 words without using "and" or "or".
  3. Pick a concept that appears under several different names in your code, and standardise on one.

Functions

Small, well-named, and doing exactly one thing

Functions are the first line of organisation in any program. The first rule of functions is that they should be small. The second rule is that they should be smaller than that. In the 1980s we said a function should fit on a screen — 24 lines by 80 columns. Today, with big monitors, we can fit far more, but we should not. Functions should hardly ever be 20 lines long. Kent Beck's Sparkle program had functions of two, three, or four lines. Each was transparently obvious, each told a story, and each led you to the next in a compelling order.

Blocks within if, else, and while statements should be one line long. That line should probably be a function call with a nicely descriptive name. This keeps the enclosing function small and adds documentary value. The indent level of a function should not be greater than one or two.

Functions should do one thing. They should do it well. They should do it only. But what is "one thing"? If a function performs only those steps that are one level below the stated name of the function, then it is doing one thing. A good way to know that a function is doing more than one thing is if you can extract another function from it with a name that is not merely a restatement of its implementation. Sections within a function — declarations, initialisations, sieve — are another symptom of doing more than one thing.

To make sure our functions are doing one thing, we need each statement within the function to be at the same level of abstraction. Mixing levels within a function is always confusing. Readers cannot tell whether a particular expression is an essential concept or a detail. Worse, once details are mixed with essential concepts, more and more details tend to accrete within the function.

We want code to read like a top-down narrative. Every function should be followed by those at the next level of abstraction, so that we can read the program one level at a time. This is the Step-down Rule.

Arguments are hard. The ideal number of arguments is zero. Next comes one, then two. Three should be avoided where possible; more than three requires very special justification. Flag arguments are ugly — passing a boolean into a function is a truly terrible practice, because it loudly proclaims that the function does more than one thing.

Side effects are lies. A function promises to do one thing, but it also does other hidden things. Sometimes it makes unexpected changes to its own class, or to its parameters, or to system globals. Temporal couplings are especially confusing when hidden as a side effect. Prefer exceptions to returning error codes: the error processing code can be separated from the happy path, and the code can be simplified. Extract the bodies of try and catch blocks into functions of their own. Error handling is one thing — a function that handles errors should do nothing else.

Duplication may be the root of all evil in software. Many principles and practices — Codd's normal forms, object-oriented programming, structured programming, aspect-oriented programming — exist at least in part to eliminate it.

// Bad: long, mixed levels of abstraction, flag argument
public static String testableHtml(
    PageData pageData, boolean includeSuiteSetup) throws Exception {
  // 30+ lines of buffer manipulation, path building, HTML generation
}

// Good: small, one level of abstraction, no flags
public static String renderPageWithSetupsAndTeardowns(
    PageData pageData, boolean isSuite) throws Exception {
  if (isTestPage(pageData))
    includeSetUpAndTeardownPages(pageData, isSuite);
  return pageData.getHtml();
}

When you write functions, they come out long and complicated. Then you massage and refine them, splitting out functions, changing names, eliminating duplication. You don't write them clean to start — nobody could.

Key Ideas

  • Functions should be small — very small — and do one thing.
  • One level of abstraction per function, following the Step-down Rule.
  • Few arguments: niladic, monadic, dyadic; avoid triads and flag arguments.
  • Have no side effects; prefer exceptions to error codes.
  • Duplication is the root of much evil — eliminate it.

Try It Yourself

  1. Take a 50-line function and extract three smaller ones.
  2. Explain what render(true) does, without reading the function body.
  3. Write an isEligibleForFullBenefits() function that explains a complex conditional.

Comments

Don't comment bad code — rewrite it

Nothing can be quite so helpful as a well-placed comment. Nothing can clutter up a module more than frivolous dogmatic comments. Nothing can be so damaging as an old, crufty comment that propagates lies and misinformation. Comments are, at best, a necessary evil. If our programming languages were expressive enough, or if we had the talent to subtly wield them, we would not need comments very much — perhaps not at all.

The proper use of comments is to compensate for our failure to express ourselves in code. Note the word failure. I meant it. Comments are always failures. We must have them because we cannot always figure out how to express ourselves without them, but their use is not a cause for celebration.

Why am I so down on comments? Because they lie. Not always, not intentionally, but too often. The older a comment is, and the farther away it is from the code it describes, the more likely it is to be wrong. Programmers cannot realistically maintain them. Code changes and evolves; the comments don't always follow. Inaccurate comments are far worse than no comments at all. Truth can only be found in one place: the code.

Some comments are necessary or beneficial. Legal comments — copyright and authorship statements — are reasonable. Informative comments, such as a regex that matches a date, can help. Explanation of intent — why a decision was made — is valuable. Clarification of an obscure argument or return value can help when you cannot change the code. Warning of consequences — "don't run unless you have time to kill" — is useful. TODO comments are reasonable as reminders. Amplification — pointing out why something that looks inconsequential matters — can help. Well-written Javadocs in public APIs are invaluable.

Bad comments fall into many categories. Mumbling — a comment plopped in because the process requires it — helps no one. Redundant comments restate what the code already says. Misleading comments are worse than no comment at all. Mandated comments — a Javadoc on every function — clutter up the code. Journal comments — change logs at the top of a module — belong in source code control. Noise comments — "the default constructor" — state the obvious. Position markers, closing brace comments, and attributions are clutter. Commented-out code is an abomination; the source code control system remembers it for you. HTML comments in source code are hard to read in the editor. Nonlocal information — system-wide context in a local comment — is misleading. Too much information — a comment that rambles — is noise. Inobvious connections — comments that no longer connect to the code — are dead weight. Function headers — when a good name would do — are unnecessary.

// Bad: redundant
i++; // increment i

// Bad: misleading (returns true, not "when this.closed is true")
// Utility method that returns when this.closed is true.
public synchronized void waitForClose(final long timeoutMillis) { /* ... */ }

// Good: explains intent
// format matched kk:mm:ss EEE, MMM dd, yyyy
Pattern timeMatcher = Pattern.compile(
  "\\d*:\\d*:\\d* \\w*, \\w* \\d*, \\d*");

// Good: don't use a comment when you can use a function
// Before:
// Check to see if the employee is eligible for full benefits
if ((employee.flags & HOURLY_FLAG) && (employee.age > 65))

// After:
if (employee.isEligibleForFullBenefits())

Clear and expressive code with few comments is far superior to cluttered and complex code with lots of comments. Rather than spend your time writing comments that explain the mess you've made, spend it cleaning that mess.

Key Ideas

  • Comments are, at best, a necessary evil — a failure to express ourselves in code.
  • Good comments: legal, informative, explanation of intent, warning, TODO, Javadocs in public APIs.
  • Bad comments: redundant, misleading, mandated, noise, commented-out code.
  • Don't use a comment when a function or variable would do.
  • Explain yourself in code; let the names and structure carry the message.

Try It Yourself

  1. Find a comment in your code and see whether you can eliminate it by renaming a variable or extracting a function.
  2. Delete a block of commented-out code — your source control system still remembers it.
  3. Convert a "what" comment into a "why" comment, or eliminate it.

Formatting

Communication is the professional developer's first order of business

When people look under the hood of your code, you want them to be impressed with the neatness, consistency, and attention to detail. You want them to perceive that professionals have been at work. If instead they see a scrambled mass of code that looks like it was written by a bevy of drunken sailors, they are likely to conclude that the same inattention to detail pervades every other aspect of the project.

Vertical formatting begins with file size. FitNesse, at nearly 50,000 lines, is built out of files that are typically 200 lines long, with an upper limit of 500. Small files are easier to understand than large files are. The newspaper metaphor helps: the name of a source file should be simple but explanatory; the topmost parts should provide the high-level concepts and algorithms; detail should increase as you move downward.

Nearly all code is read left to right and top to bottom. Each line represents an expression, and each group of lines represents a complete thought. Those thoughts should be separated from each other with blank lines. Vertical density, on the other hand, implies close association — lines of code that are tightly related should appear vertically dense. Concepts that are closely related should be kept vertically close to each other.

Variable declarations should be as close to their usage as possible. Control variables for loops should usually be declared within the loop statement. Instance variables, on the other hand, should be declared at the top of the class, so that everyone knows where to go to see them.

Horizontal formatting: how wide should a line be? Analysis of seven projects shows a remarkable regularity around 45 characters, with a long tail above 80. The old Hollerith limit of 80 is a bit arbitrary, and I am not opposed to lines edging out to 100 or even 120 — but beyond that is probably careless. Use horizontal white space to associate things that are strongly related and to disassociate things that are more weakly related.

Indentation is the way we make the hierarchy of scopes visible. Without indentation, programs would be virtually unreadable by humans. Don't break indentation for short if statements or short functions — expand and indent instead. Dummy scopes should be properly indented and surrounded by braces; a semicolon silently sitting at the end of a while loop on the same line is too easy to miss.

A team of developers should agree on a single formatting style, and every member should use it. The title of this section is a play on words: every programmer has favourite rules, but if he works in a team, the team rules.

// Good: each function fits on one screen; concepts separated by blank lines
private void measureLine(String line) {
  lineCount++;
  int lineSize = line.length();
  totalChars += lineSize;
  lineWidthHistogram.addLine(lineSize, lineCount);
  recordWidthLine(lineSize);
}

// Good: prefer unaligned assignments — the list length tells a story
public class FitNesseExpediter implements ResponseSender {
  private Socket socket;
  private InputStream input;
  private OutputStream output;
  private Request request;
  // ...
}

Remember: a good software system is composed of a set of documents that read nicely. They need to have a consistent and smooth style. The last thing we want to do is add more complexity to the source code by writing it in a jumble of different individual styles.

Key Ideas

  • Formatting is about communication — treat it as a first-class concern.
  • Vertical: small files (≈200 lines typical, 500 max), newspaper metaphor, blank lines between concepts, density where appropriate.
  • Horizontal: short lines (≈120 characters max), white space to show association, indentation to show hierarchy.
  • Team rules override personal preference — agree on a style and encode it in your formatter.

Try It Yourself

  1. Count the lines in the largest source file you own. If it is over 500, find a way to split it.
  2. Add blank lines between the package declaration, the imports, and each method in a file.
  3. Agree on a brace style with your team and configure your formatter to enforce it.

Objects and Data Structures

Objects hide data; data structures expose it

There is a reason we keep our variables private: we don't want anyone else to depend on them. We want the freedom to change their type or implementation on a whim. So why do so many programmers automatically add getters and setters, exposing their private variables as though they were public?

Consider two representations of a point on the Cartesian plane. The first exposes its implementation — public double x; and public double y;. The second hides it behind an interface: double getX();, double getY();, void setCartesian(double x, double y);, double getR();, double getTheta();, void setPolar(double r, double theta);. With the first, you can tell the implementation is rectangular. With the second, you cannot tell whether the implementation is rectangular or polar — and it does not matter.

Hiding implementation is not just a matter of putting a layer of functions between the variables. Hiding implementation is about abstractions. A class does not simply push its variables out through getters and setters. Rather, it exposes abstract interfaces that allow its users to manipulate the essence of the data, without having to know its implementation.

This exposes a fundamental dichotomy between objects and data structures. Objects hide their data behind abstractions and expose functions that operate on that data. Data structures expose their data and have no meaningful functions. The two are virtual opposites.

Procedural code (using data structures) makes it easy to add new functions without changing the existing data structures. OO code makes it easy to add new classes without changing existing functions. The complement is also true: procedural code makes it hard to add new data structures because all the functions must change; OO code makes it hard to add new functions because all the classes must change. Mature programmers know that the idea that everything is an object is a myth. Sometimes you really do want simple data structures with procedures operating on them.

The Law of Demeter says that a module should not know about the innards of the objects it manipulates. More precisely, a method f of a class C should only call the methods of C, of an object created by f, of an object passed as an argument to f, or of an object held in an instance variable of C. The method should not invoke methods on objects that are returned by any of the allowed functions. In other words, talk to friends, not to strangers.

Chains of calls like ctxt.getOptions().getScratchDir().getAbsolutePath() are often called train wrecks. Split them up. If ctxt, Options, and ScratchDir are objects, their internal structure should be hidden. If they are just data structures with no behaviour, then Demeter does not apply.

Hybrids — half object, half data structure — are the worst of both worlds. They make it hard to add new functions and hard to add new data structures. Avoid creating them. And remember: the quintessential form of a data structure is the Data Transfer Object, a class with public variables and no functions. Active Records are special forms of DTOs — data structures with public variables but with navigational methods like save and find. Treat them as data structures, and create separate objects for business rules.

// Train wreck — violates the Law of Demeter
final String outputDir = ctxt.getOptions().getScratchDir().getAbsolutePath();

// Better: split it up
Options opts = ctxt.getOptions();
File scratchDir = opts.getScratchDir();
final String outputDir = scratchDir.getAbsolutePath();

// Even better: tell, don't ask
BufferedOutputStream bos = ctxt.createScratchFileStream(classFileName);

Key Ideas

  • Objects hide data and expose behaviour; data structures expose data and have no behaviour.
  • Objects make it easy to add new types; data structures make it easy to add new functions.
  • Law of Demeter: talk to friends, not strangers; avoid train wrecks.
  • Avoid hybrids that are half object, half data structure.
  • Use DTOs for pure data transfer; treat Active Records as data structures.

Try It Yourself

  1. Take a class with public fields and hide them behind behaviour — not just getters and setters.
  2. Find a train wreck in your code and split it up, or better: replace it with a message to the first object.
  3. Classify three classes in your project as objects or data structures. Are any hybrids? Refactor them.

Error Handling

If error handling obscures logic, it's wrong

Error handling is just one of those things that we all have to do when we program. Input can be abnormal and devices can fail. In short, things can go wrong, and when they do, we as programmers are responsible for making sure our code does what it needs to do. The connection to clean code is clear: many code bases are completely dominated by error handling, so that it is nearly impossible to see what the code does. Error handling is important, but if it obscures logic, it's wrong.

Back in the distant past, many languages didn't have exceptions. You either set an error flag or returned an error code that the caller could check. The problem with these approaches is that they clutter the caller — the caller must check for errors immediately after the call. It is better to throw an exception when you encounter an error. The calling code is cleaner, and two concerns that were tangled — the algorithm and error handling — are now separated.

Write your try-catch-finally statement first. When you execute code in the try portion, you are stating that execution can abort at any point and then resume at the catch. In a way, try blocks are like transactions: your catch has to leave your program in a consistent state, no matter what happens. Start with a try-catch-finally statement; use TDD to force exceptions, and add behaviour to your handler to satisfy your tests.

Use unchecked exceptions. The price of checked exceptions is an Open/Closed Principle violation. If you throw a checked exception from a method in your code, and the catch is three levels above, you must declare that exception in the signature of each method between you and the catch. This means a change at a low level of the software can force signature changes on many higher levels. Encapsulation is broken because all functions in the path of a throw must know about details of that low-level exception.

Each exception you throw should provide enough context to determine the source and location of an error. Create informative error messages and pass them along with your exceptions. Define exception classes in terms of a caller's needs. Often a single exception class is fine for a particular area of code — the information sent with the exception can distinguish the errors. Wrapping third-party APIs is a best practice: you minimise your dependencies on it, and you can define the API you are comfortable with.

Define the normal flow. In business applications, some code paths are not exceptional — a per-diem meal expense, for example, is a normal part of the business, not an error. Use the Special Case Pattern: create a class or configure an object that handles a special case for you. The client code doesn't have to deal with exceptional behaviour.

Don't return null. When we return null, we are essentially creating work for ourselves and foisting problems upon our callers. If you are tempted to return null, consider throwing an exception or returning a special case object instead. Don't pass null either: unless you are working with an API that expects it, you should avoid passing null in your code whenever possible.

// Bad: error codes clutter the caller
if (deletePage(page) == E_OK) {
  if (registry.deleteReference(page.name) == E_OK) {
    if (configKeys.deleteKey(page.name.makeKey()) == E_OK) {
      logger.log("page deleted");
    } else {
      logger.log("configKey not deleted");
    }
  } else {
    logger.log("deleteReference from registry failed");
  }
} else {
  logger.log("delete failed");
  return E_ERROR;
}

// Good: exceptions separate the happy path
try {
  deletePage(page);
  registry.deleteReference(page.name);
  configKeys.deleteKey(page.name.makeKey());
} catch (Exception e) {
  logger.log(e.getMessage());
}

Key Ideas

  • Error handling is a separate concern; keep it from obscuring logic.
  • Prefer exceptions to returning error codes.
  • Write the try-catch-finally statement first; it defines a transaction scope.
  • Use unchecked exceptions, provide context with exceptions, and define exception classes by caller needs.
  • Don't return null and don't pass null.

Try It Yourself

  1. Replace an error-code return with a thrown exception, and simplify the caller.
  2. Wrap a third-party API so that it throws a single exception type of your own.
  3. Find a null check that could be replaced by returning an empty collection.

Boundaries

Clean integration with code you don't control

We seldom control all the software in our systems. Sometimes we buy third-party packages or use open source. Other times we depend on teams in our own company to produce components or subsystems for us. Somehow we must cleanly integrate this foreign code with our own.

There is a natural tension between the provider of an interface and the user of an interface. Providers of third-party packages and frameworks strive for broad applicability so they can work in many environments and appeal to a wide audience. Users, on the other hand, want an interface that is focused on their particular needs. This tension can cause problems at the boundaries of our systems.

Take java.util.Map. It has a very broad interface with plenty of capabilities. If our application builds up a Map and passes it around, any user of that Map has the power to clear() it, and Maps do not reliably constrain the types of objects placed within them. A cleaner way to use Map might be to hide it inside a Sensors class — the interface at the boundary is hidden, and the use of generics is no longer a big issue because the casting and type management is handled inside the Sensors class.

Learning third-party code is hard, and integrating it is hard too. Doing both at the same time is doubly hard. Instead of experimenting and trying out the new stuff in production code, write learning tests — tests that call the third-party API the way you expect to use it in your application. These tests focus on what you want out of the API, and they end up costing nothing: you had to learn the API anyway, and the tests verify that the third-party packages work the way you expect them to. When there are new releases of the third-party package, you run the learning tests to see whether there are behavioural differences.

There is another kind of boundary, one that separates the known from the unknown. Sometimes what is on the other side of the boundary is unknowable. The team I worked with was developing software for a radio communications system, and there was a subsystem — the "Transmitter" — that we knew little about, and the people responsible had not defined their interface. Rather than being blocked, we defined our own interface, Transmitter, with a method transmit(frequency, stream). We wrote the interface we wished we had. When the transmitter API was finally defined, we wrote an Adapter to bridge the gap. Code at the boundaries needs clear separation and tests that define expectations.

// Clean boundary: hide Map behind a class
public class Sensors {
  private Map sensors = new HashMap();

  public Sensor getById(String id) {
    return (Sensor) sensors.get(id);
  }
}

// Adapter for an unknown subsystem
public interface Transmitter {
  void transmit(double frequency, InputStream data);
}

public class TransmitterAdapter implements Transmitter {
  private final TransmitterApi api;

  public void transmit(double frequency, InputStream data) {
    // Translate our interface into the vendor's API
    api.setFrequency(frequency);
    api.sendStream(data);
  }
}

Key Ideas

  • Third-party code has a natural tension with your needs.
  • Keep boundary interfaces inside the class or close family of classes where they are used.
  • Write learning tests for third-party code — they end up costing nothing.
  • Use the Adapter pattern to wrap unknown or not-yet-designed APIs.
  • Clean boundaries need clear separation and tests that define expectations.

Try It Yourself

  1. Wrap a Map or similar generic interface in your codebase behind a class of your own.
  2. Write a learning test for a library you are using.
  3. Define the interface you wish you had for an unknown subsystem, and write an Adapter for it.

Unit Tests

Test code is just as important as production code

Our profession has come a long way. In 1997 no one had heard of Test Driven Development. Unit tests were short bits of throwaway code that we wrote to make sure our programs "worked." Today, TDD is one of our most fundamental disciplines — but in the mad rush to add testing, many programmers have missed some of the more subtle, and important, points of writing good tests.

The Three Laws of TDD: First, you may not write production code until you have written a failing unit test. Second, you may not write more of a unit test than is sufficient to fail — not compiling is failing. Third, you may not write more production code than is sufficient to pass the currently failing test. These three laws lock you into a cycle that is perhaps thirty seconds long.

Test code is just as important as production code. It is not a second-class citizen. It requires thought, design, and care. It must be kept as clean as production code. The team I coached decided that their test code should not be maintained to the same standards of quality as their production code — "quick and dirty" was the watchword. What they did not realise was that having dirty tests is equivalent to, if not worse than, having no tests. The dirtier the tests, the harder they are to change. Eventually the team discarded the test suite entirely, and their defect rate began to rise.

What makes a clean test? Readability, readability, and readability. What makes tests readable is the same thing that makes all code readable: clarity, simplicity, and density of expression. Build a domain-specific testing language — a set of functions and utilities that make the tests convenient to write and easier to read. Build-Operate-Check: each test is clearly split into three parts — the data, the operation, and the check.

One assert per test is a good guideline, but not a rule. One concept per test is better. Don't write long test functions that go testing one miscellaneous thing after another. Test a single concept in each test function.

F.I.R.S.T.: Fast (tests should run quickly), Independent (tests should not depend on each other), Repeatable (tests should be repeatable in any environment), Self-Validating (tests should have a boolean output), and Timely (tests need to be written in a timely fashion — just before the production code that makes them pass). If you let the tests rot, then your code will rot too.

// Clean test with a domain-specific language
@Test
public void turnOnLoTempAlarmAtThreshold() throws Exception {
  wayTooCold();
  assertEquals("HBchL", hw.getState());
}

// Instead of many asserts scattered across a long test:
@Test
public void testGetPageHierarchyAsXml() throws Exception {
  makePages("PageOne", "PageOne.ChildOne", "PageTwo");
  submitRequest("root", "type:pages");
  assertResponseIsXML();
  assertResponseContains(
    "<name>PageOne</name>",
    "<name>PageTwo</name>",
    "<name>ChildOne</name>"
  );
}

Key Ideas

  • Three Laws of TDD: fail first, just enough test, just enough code.
  • Test code is as important as production code — keep it clean.
  • Tests enable the -ilities; dirty tests slow you down, then stop you.
  • One concept per test; use domain-specific testing language; minimise asserts.
  • F.I.R.S.T.: Fast, Independent, Repeatable, Self-Validating, Timely.

Try It Yourself

  1. Refactor a messy test using a domain-specific language of your own.
  2. Split a test that checks multiple concepts into separate tests.
  3. Time a single test. If it is slow, make it faster.

Part One · Principles, Patterns, and Practices · Chapter 10

Classes

Small, single-purpose, and organised for change

Following the standard Java convention, a class should begin with a list of variables. Public static constants first, then private static variables, then private instance variables. Public functions follow the list of variables, with the private utilities called by a public function right after the public function itself. This follows the step-down rule and helps the program read like a newspaper article. We like to keep our variables and utility functions private, but we're not fanatics — tests rule. If a test in the same package needs to call a function or access a variable, we'll make it protected or package scope. Loosening encapsulation is always a last resort.

The first rule of classes is that they should be small. The second rule is that they should be smaller than that. With functions, we measured size by counting physical lines. With classes, we count responsibilities. The SuperDashboard class in the book exposes about 70 public methods — most developers would agree that it is a "God class." But even a five-method class can have too many responsibilities. The name of a class should describe what responsibility it fulfils. If we cannot derive a concise name, then it is likely too large. We should also be able to write a brief description of the class in about 25 words, without using the words "if," "and," "or," or "but."

The Single Responsibility Principle (SRP) states that a class or module should have one, and only one, reason to change. This principle gives us both a definition of responsibility and a guideline for class size. SuperDashboard tracks version information and manages Swing components — two reasons to change. Extract the version information into its own Version class, and the class becomes reusable elsewhere. SRP is one of the more important concepts in OO design, and one of the simpler to understand — yet it is often the most abused. Getting software to work and making software clean are two very different activities.

Cohesion: classes should have a small number of instance variables, and each method should manipulate one or more of those variables. In general, the more variables a method manipulates, the more cohesive that method is to its class. A class in which each variable is used by each method is maximally cohesive. When cohesion is high, the methods and variables of the class are co-dependent and hang together as a logical whole. Maintaining cohesion results in many small classes: split a large function into many smaller functions, and you often get the opportunity to split several smaller classes out as well.

Organising for change: for most systems, change is continual. Every change subjects us to the risk that the remainder of the system no longer works as intended. In a clean system we organise our classes so as to reduce the risk of change. The Sql class is a good example: it must change when we add a new type of statement, and it must change when we alter the details of a single statement type. Two reasons to change — a clear SRP violation. The solution is a set of closed classes, each with a single responsibility, supporting the Open-Closed Principle: classes should be open for extension but closed for modification.

Isolating from change: needs will change, therefore code will change. A client class depending on concrete details is at risk when those details change. Introduce interfaces and abstract classes to help isolate the impact. The Dependency Inversion Principle (DIP) says our classes should depend upon abstractions, not on concrete details.

// Extract version information into its own single-responsibility class
public class Version {
  public int getMajorVersionNumber() { /* ... */ }
  public int getMinorVersionNumber() { /* ... */ }
  public int getBuildNumber() { return 0; }
}

// Depend on an abstraction, not a concrete detail
public class Portfolio {
  private StockExchange exchange;

  public Portfolio(StockExchange exchange) {
    this.exchange = exchange;
  }

  // ...
}

public interface StockExchange {
  Money currentPrice(String symbol);
}

Key Ideas

  • Classes should be small — measured by responsibilities, not lines.
  • SRP: a class should have one, and only one, reason to change.
  • High cohesion: methods and variables hang together as a logical whole.
  • Organise for change; Open-Closed Principle; DIP: depend on abstractions, not concrete details.
  • Extract smaller classes from big functions; split classes that lose cohesion.

Try It Yourself

  1. Write a 25-word description of one of your classes, without using "and" or "or".
  2. Split a class with two responsibilities into two single-responsibility classes.
  3. Refactor a class that depends on a concrete external API to depend on an interface instead.

Part One · Principles, Patterns, and Practices · Chapter 11

Systems

Staying clean at the higher levels of abstraction

Could you manage all the details of a city yourself? Probably not. Even managing an existing city is too much for one person. Yet cities work because they have teams of people who manage particular parts of the city — water systems, power systems, traffic, law enforcement, building codes. Cities also work because they have evolved appropriate levels of abstraction and modularity that make it possible for individuals and the "components" they manage to work effectively, even without understanding the big picture. Software teams are often organised like that too — but the systems they work on often don't have the same separation of concerns.

The first concern is the startup process. Software systems should separate the startup process — when the application objects are constructed and the dependencies are "wired" together — from the runtime logic that takes over after startup. Most applications don't do this: startup code is ad hoc and mixed in with the runtime logic. The LAZY INITIALIZATION idiom is the classic example. One occurrence isn't a serious problem, but there are normally many instances of little setup idioms scattered across the application, with little modularity and significant duplication.

One way to separate construction from use is simply to move all aspects of construction to main, or modules called by main, and design the rest of the system assuming that all objects have been constructed and wired up appropriately. The flow of control is easy to follow; the application has no knowledge of main or of the construction process.

Sometimes the application must be responsible for when an object gets created. In this case, use the Abstract Factory pattern to give the application control of when to build the objects, but keep the details of the construction separate from the application code. Or use Dependency Injection (DI) — the application of Inversion of Control to dependency management. The class takes no direct steps to resolve its dependencies; it is completely passive. Instead, it provides setter methods or constructor arguments (or both) that are used to inject the dependencies.

Scaling up: it is a myth that we can get systems "right the first time." Instead, we should implement only today's stories, then refactor and expand the system to implement new stories tomorrow. This is the essence of iterative and incremental agility. Software systems are unique compared to physical systems: their architectures can grow incrementally, if we maintain the proper separation of concerns.

Cross-cutting concerns: concerns like persistence, security, and transactions tend to cut across the natural object boundaries of a domain. You want to persist all your objects using generally the same strategy, but in practice you have to spread essentially the same code across many objects. Aspect-oriented programming (AOP) is a general-purpose approach to restoring modularity for cross-cutting concerns. In AOP, modular constructs called aspects specify which points in the system should have their behaviour modified in some consistent way.

Test drive the system architecture: if you can write your application's domain logic using POJOs, decoupled from any architecture concerns at the code level, then it is possible to truly test drive your architecture. You can evolve it from simple to sophisticated as needed. Use standards wisely, when they add demonstrable value. And remember: systems need domain-specific languages — small scripting languages or APIs in standard languages that permit code to be written so that it reads like a structured form of prose a domain expert might write.

// Bad: lazy initialization with a hard-coded dependency
public Service getService() {
  if (service == null)
    service = new MyServiceImpl(); // good enough for most cases?
  return service;
}

// Good: dependency injection
public class Application {
  private Service service;

  public Application(Service service) {
    this.service = service;
  }
}

Key Ideas

  • Separate construction from use; move construction to main or a factory.
  • Use Dependency Injection to invert control of dependency management.
  • Architectures can grow incrementally, if we maintain the separation of concerns.
  • Use AOP to handle cross-cutting concerns non-invasively.
  • POJOs plus aspect-like mechanisms let you test-drive the architecture.

Try It Yourself

  1. Move setup code out of a class into main or a factory.
  2. Replace a new call in business logic with an injected dependency.
  3. Identify a cross-cutting concern in your codebase and describe how you would weave it in non-invasively.

Emergence

Four simple rules that produce good design

What if there were four simple rules that you could follow that would help you create good designs as you worked? What if by following these rules you gained insights into the structure and design of your code, making it easier to apply principles such as SRP and DIP? Many of us feel that Kent Beck's four rules of Simple Design are of significant help in creating well-designed software.

According to Kent, a design is "simple" if it follows these rules, given in order of importance: Runs all the tests; Contains no duplication; Expresses the intent of the programmer; Minimises the number of classes and methods.

Runs all the tests: first and foremost, a design must produce a system that acts as intended. A system that is comprehensively tested and passes all its tests all of the time is a testable system. Making our systems testable pushes us toward a design where our classes are small and single-purpose. It's just easier to test classes that conform to the SRP. The more tests we write, the more we use principles like DIP and tools like dependency injection, interfaces, and abstraction to minimise coupling. Remarkably, following a simple and obvious rule that says we need to have tests and run them continuously impacts our system's adherence to the primary OO goals of low coupling and high cohesion.

No duplication: duplication is the primary enemy of a well-designed system. It represents additional work, additional risk, and additional unnecessary complexity. Duplication manifests in many forms. Lines of code that look exactly alike are, of course, duplication. Lines of code that are similar can often be massaged to look even more alike. And duplication can exist in other forms, such as duplication of implementation — for example, a size() method and an isEmpty() method that could be tied together. Creating a clean system requires the will to eliminate duplication, even in just a few lines of code.

Expressive: most of us have had the experience of working on convoluted code. The majority of the cost of a software project is in long-term maintenance. In order to minimise the potential for defects as we introduce change, it's critical for us to be able to understand what a system does. You can express yourself by choosing good names, by keeping functions and classes small, and by using standard nomenclature — design patterns are largely about communication and expressiveness. But the most important way to be expressive is to try. Take a little pride in your workmanship.

Minimal classes and methods: even concepts as fundamental as elimination of duplication, code expressiveness, and the SRP can be taken too far. In an effort to make our classes and methods small, we might create too many tiny classes and methods. So this rule suggests that we also keep our function and class counts low. Our goal is to keep our overall system small while also keeping our functions and classes small.

// Duplication: size() and isEmpty() track the same thing
int size() { /* ... */ }
boolean isEmpty() {
  return 0 == size();
}

// Template Method: eliminate higher-level duplication
public abstract class VacationPolicy {
  public void accrueVacation() {
    calculateBaseVacationHours();
    alterForLegalMinimums();
    applyToPayroll();
  }
  private void calculateBaseVacationHours() { /* ... */ }
  protected abstract void alterForLegalMinimums();
  private void applyToPayroll() { /* ... */ }
}

Key Ideas

  • Four rules of simple design, in order of importance: runs all tests, no duplication, expresses intent, minimises classes and methods.
  • Writing tests pushes your design toward low coupling and high cohesion.
  • Duplication is the primary enemy of a well-designed system — eliminate it.
  • Express yourself through names, small classes, standard nomenclature, and well-written tests.
  • Minimise classes and methods — but not so far that you create a swarm of tiny classes.

Try It Yourself

  1. Find duplication in your code and extract a method to eliminate it.
  2. Explain a function's intent to a colleague without reading its body.
  3. Count the classes in your last project. Are any of them doing nothing? Delete them.

Concurrency

Clean concurrent code is hard — very hard

Writing clean concurrent programs is hard — very hard. It is much easier to write code that executes in a single thread. It is also easy to write multithreaded code that looks fine on the surface but is broken at a deeper level. Such code works fine until the system is placed under stress.

Why concurrency? Concurrency is a decoupling strategy. It helps us decouple what gets done from when it gets done. From a structural point of view, the application looks like many little collaborating computers rather than one big main loop. This can make the system easier to understand and offers some powerful ways to separate concerns. Some systems have response time and throughput constraints that require hand-coded concurrent solutions.

Myths and misconceptions: concurrency does not always improve performance — it only helps when there is a lot of wait time that can be shared. Design does change when writing concurrent programs. And understanding concurrency issues is important when working with a container. Concurrency incurs overhead, correct concurrency is complex even for simple problems, and concurrency bugs aren't usually repeatable — so they are often ignored as one-offs instead of the true defects they are.

Defense principles: follow the Single Responsibility Principle — keep concurrency-related code separate from other code. Limit the scope of data; take data encapsulation to heart. Use copies of data — avoid sharing the data in the first place. Make threads as independent as possible — each thread processes one client request with all of its required data coming from an unshared source.

Know your library. Java 5 offers many improvements: use the provided thread-safe collections, use the Executor framework for executing unrelated tasks, use nonblocking solutions when possible, and be aware that several library classes are not thread safe. Know your execution models: producer-consumer, readers-writers, dining philosophers. Beware dependencies between synchronized methods: if there is more than one synchronized method on the same shared class, then your system may be written incorrectly. Keep synchronized sections small: extending synchronization beyond the minimal critical section increases contention and degrades performance.

Writing correct shut-down code is hard. Graceful shutdown can be hard to get correct, with threads waiting for a signal to continue that never comes. Think about shutdown early and get it working early.

Testing threaded code: treat spurious failures as candidate threading issues. Get your nonthreaded code working first. Make your threaded code pluggable and tunable. Run with more threads than processors, run on different platforms, and instrument your code to try and force failures — by hand or with automated tools like ConTest. The point is to jiggle the code so that threads run in different orderings at different times.

// The ++ operator is not atomic!
public class IdGenerator {
  int lastIdUsed;

  public int incrementValue() {
    return ++lastIdUsed;
  }
}

// Fix it with synchronized
public class IdGenerator {
  int lastIdUsed;

  public synchronized int incrementValue() {
    return ++lastIdUsed;
  }
}

Key Ideas

  • Concurrency decouples what from when; it can improve throughput and structure.
  • Follow SRP: keep concurrency code separate; limit the scope of shared data.
  • Know your library: thread-safe collections, Executor framework, nonblocking solutions.
  • Keep synchronized sections small; beware dependencies between synchronized methods.
  • Test threaded code with jiggling — force failures with instrumentation.

Try It Yourself

  1. Find shared mutable state in your code and limit its scope.
  2. Replace a hand-rolled thread pool with an Executor.
  3. Add a jiggle point to a test to force different orderings.

Successive Refinement

A command-line argument parser, written and rewritten

This chapter is a case study in successive refinement. You will see a module that started well but did not scale. Then you will see how the module was refactored and cleaned. Most of us have had to parse command-line arguments from time to time. There are several good utilities available, but none of them do exactly what I want — so I decided to write my own. I call it Args.

You simply construct the Args class with the input arguments and a format string, and then query the Args instance for the values of the arguments. The format string "l,p#,d*" defines three command-line arguments: -l is a boolean argument, -p is an integer argument, and -d is a string argument. If the constructor returns without throwing an ArgsException, then the incoming command-line was parsed, and the Args instance is ready to be queried. Methods like getBoolean, getInt, and getString allow us to access the values.

But writing clean code is not the same as writing code. My first version was a mess. It had a bewildering number of instance variables, odd strings like "TILT," and try-catch-catch blocks that added up to a festering pile. Earlier versions had been much simpler — when only Boolean arguments were supported, the code was compact and easy to understand. Adding just two more argument types — String and integer — had a massively negative impact. It converted something reasonably maintainable into something I expected to become riddled with bugs.

So I stopped. I had at least two more argument types to add, and I could tell that they would make things much worse. If the structure of this code was ever going to be maintainable, now was the time to fix it. So I stopped adding features and started refactoring.

Having just added the String and integer arguments, I knew that each argument type required new code in three major places. First, each argument type required some way to parse its schema element in order to select the HashMap for that type. Next, each argument type needed to be parsed in the command-line strings and converted to its true type. Finally, each argument type needed a getXXX method so that it could be returned to the caller as its true type. Many different types, all with similar methods — that sounds like a class to me. And so the ArgumentMarshaler concept was born.

The key discipline is incrementalism. One of the best ways to ruin a program is to make massive changes to its structure in the name of improvement. To avoid this, I use Test Driven Development. In other words, using TDD, I am not allowed to make a change to the system that breaks that system. Every change I make must keep the system working as it worked before. So I proceeded to make a large number of very tiny changes. Each change moved the structure of the system toward the ArgumentMarshaler concept. And yet each change kept the system working.

// After refactoring: clean argument parsing with marshalers
public class Args {
  private Map<Character, ArgumentMarshaler> marshalers;
  private Set<Character> argsFound;

  public boolean getBoolean(char arg) {
    ArgumentMarshaler am = marshalers.get(arg);
    return am != null && (Boolean) am.get();
  }

  public String getString(char arg) {
    ArgumentMarshaler am = marshalers.get(arg);
    return am == null ? "" : (String) am.get();
  }

  public int getInt(char arg) {
    ArgumentMarshaler am = marshalers.get(arg);
    return am == null ? 0 : (Integer) am.get();
  }
}

It is not enough for code to work. Code that works is often badly broken. Programmers who satisfy themselves with merely working code are behaving unprofessionally. Nothing has a more profound and long-term degrading effect upon a development project than bad code.

Key Ideas

  • Write a rough draft first, then clean it up through successive refinement.
  • TDD keeps the system running at all times — every change must keep tests passing.
  • Incrementalism: tiny changes, each verified, compound into large improvements.
  • Push polymorphic behaviour into derivatives; replace the type-switch with a marshaller.
  • Code that works is not enough — keep it clean or it will drag the team down.

Try It Yourself

  1. Write a rough-draft parser for a tiny command-line, then refactor it after tests pass.
  2. Apply the Marshaler pattern to a type-switch in your own code.
  3. Commit only when all tests pass — try it for a week.

JUnit Internals

Even good code can be a little cleaner

JUnit is one of the most famous of all Java frameworks. As frameworks go, it is simple in conception, precise in definition, and elegant in implementation. But what does the code look like? In this chapter we critique an example drawn from the JUnit framework. JUnit has had many authors, but it began with Kent Beck and Eric Gamma together on a plane to Atlanta. Kent wanted to learn Java, and Eric wanted to learn about Kent's Smalltalk testing framework.

The module we look at is the clever bit of code that helps identify string comparison errors. It is called ComparisonCompactor. Given two strings that differ, such as ABCDE and ABXDE, it will expose the difference by generating a string such as <...B[X]D...>. The code for ComparisonCompactor is nicely partitioned, reasonably expressive, and simple in structure. I ran a code coverage analysis on it using the tests. The code is 100 percent covered. This gives me a high degree of confidence that the code works and a high degree of respect for the craftsmanship of the authors.

But the Boy Scout Rule tells us we should leave the module cleaner than we found it. So how can we improve on the original code? The first thing I don't care for is the f prefix for the member variables. Today's environments make this kind of scope encoding redundant, so let's eliminate all the f's. Next, there is an unencapsulated conditional at the beginning of the compact function — extract a method that explains it.

The name of the function is strange. Although it does compact the strings, it actually might not compact them if canBeCompacted returns false. So naming it compact hides the side effect of the error check. The name should really be formatCompactedComparison. The body of the if statement is where the true compacting is done — extract that as compactExpectedAndActual.

Careful inspection of findCommonSuffix exposes a hidden temporal coupling: it depends on the fact that prefixIndex is calculated by findCommonPrefix. If the two functions were called out of order, there would be a difficult debugging session ahead. So expose this temporal coupling — by merging them into findCommonPrefixAndSuffix, or by passing the prefix as an argument.

As I was eliminating the +1s, I noticed that an if statement in compactString was nonfunctional — suffixIndex could never be less than one. This calls into question both if statements in compactString. So comment them out and run the tests. They passed! So restructure compactString to eliminate the extraneous if statements.

This is actually quite pretty. The module is separated into a group of analysis functions and another group of synthesis functions. They are topologically sorted so that the definition of each function appears just after it is used. If you look carefully, you will notice that I reversed several of the decisions I made earlier in the chapter. This is typical. Often one refactoring leads to another that leads to the undoing of the first. Refactoring is an iterative process full of trial and error, inevitably converging on something that we feel is worthy of a professional.

// Final ComparisonCompactor — analysis functions first, synthesis functions last
public class ComparisonCompactor {
  private static final String ELLIPSIS = "...";
  private static final String DELTA_END = "]";
  private static final String DELTA_START = "[";

  private int contextLength;
  private String expected;
  private String actual;
  private int prefixLength;
  private int suffixLength;

  public String formatCompactedComparison(String message) {
    String compactExpected = expected;
    String compactActual = actual;

    if (shouldBeCompacted()) {
      findCommonPrefixAndSuffix();
      compactExpected = compact(expected);
      compactActual = compact(actual);
    }
    return Assert.format(message, compactExpected, compactActual);
  }

  private boolean shouldBeCompacted() {
    return !shouldNotBeCompacted();
  }

  private boolean shouldNotBeCompacted() {
    return expected == null ||
           actual == null ||
           expected.equals(actual);
  }

  // ... findCommonPrefixAndSuffix, compact, startingEllipsis, delta, etc.
}

Key Ideas

  • Even well-written code can be improved — apply the Boy Scout Rule.
  • Extract functions to separate analysis from synthesis.
  • Expose hidden temporal couplings by merging related functions or passing arguments.
  • Eliminate dead code — extraneous if statements, unused variables.
  • Refactoring is iterative; it often undoes earlier decisions as understanding grows.

Try It Yourself

  1. Take a working module and apply the Boy Scout Rule — improve one thing.
  2. Identify dead code in a recent file and delete it.
  3. Find a +1 in your own code and see whether renaming or restructuring can eliminate it.

Refactoring SerialDate

Small refactorings compound into large improvements

If you go to the JCommon library, you will find a package named org.jfree.date, and within that package there is a class named SerialDate. The author is David Gilbert — an experienced and competent programmer who shows a significant degree of professionalism and discipline within his code. For all intents and purposes, this is "good code." And I am going to rip it to pieces. This is not an activity of malice. It is a professional review — something we should all be comfortable doing, and something we should welcome when it is done for us.

SerialDate is a class that represents a date in Java. Why have such a class, when Java already has java.util.Date and java.util.Calendar? Because java.util.Date can be too precise — it represents an instant in time, accurate to 1/1000th of a second. Sometimes we just want to represent a particular day, without concerning ourselves about the time of day, or the timezone, or anything else. That's what SerialDate is for.

The first step is to "make it work." The unit tests in SerialDateTests all pass. Unfortunately a quick inspection shows that they don't test everything. So I wrote my own suite of completely independent unit tests. Even with some of the tests commented out, Clover reports that the new unit tests are executing 170 out of the 185 executable statements. Good — now we can refactor.

Then, "make it right." We walk from the top to the bottom of SerialDate, improving it as we go. The opening comment is long out of date, so shorten it. The change history is a leftover from the 1960s — source code control remembers it. The class name SerialDate implies an implementation; the class is abstract and there is good reason to hide the implementation. I choose DayDate as the best compromise. MonthConstants should really be an enum, so change it to one — this lets us get rid of isValidMonthCode and all the month code error checking.

The comment on line 93 is redundant — redundant comments are just places to collect lies and misinformation. The comments at line 97 and line 100 talk about serial numbers. The variables they describe are the earliest and latest possible dates that DayDate can describe. But EARLIEST_DATE_ORDINAL is 2, not 0 — the explanation is in a derivative called SpreadsheetDate, and it has nothing to do with DayDate. So move those variables down into SpreadsheetDate.

The next variables — MINIMUM_YEAR_SUPPORTED and MAXIMUM_YEAR_SUPPORTED — provide something of a dilemma. A user of an abstract class needs information about its implementation. The solution is the Abstract Factory pattern: a DayDateFactory that creates DayDate instances and can answer questions about the implementation.

The day constants should really be another enum. The tables — LAST_DAY_OF_MONTH, AGGREGATE_DAYS_TO_END_OF_MONTH, and so on — can be moved or made private. The three sets of constants can be turned into enums: WeekInMonth, DateInterval, and WeekdayRange. You might not agree with the names I've chosen, but they are now in a form that makes them easy to change — they aren't passed as integers anymore; they are passed as symbols.

The rest of the refactoring is a long series of small changes. A description field is deleted; so is the default constructor. The isLeapYear method is made more expressive. The addDays, addMonths, and addYears methods are converted from static to instance. The getPreviousDayOfWeek, getFollowingDayOfWeek, and getNearestDayOfWeek methods are simplified. The weekInMonthToString and relativeToString methods are moved to enums and eventually deleted. The abstract methods are pulled up from SpreadsheetDate into DayDate. And the magic number 1 is replaced with Month.JANUARY.toInt() or Day.SUNDAY.toInt().

// Before: scattered constants and int-based month codes
public abstract class SerialDate implements Comparable, Serializable, MonthConstants {
  public static final int MONDAY = Calendar.MONDAY;
  // ...
}

// After: enums and polymorphism
public enum Month {
  JANUARY(1), FEBRUARY(2), MARCH(3),
  APRIL(4), MAY(5), JUNE(6),
  JULY(7), AUGUST(8), SEPTEMBER(9),
  OCTOBER(10), NOVEMBER(11), DECEMBER(12);

  public int quarter() {
    return 1 + (index - 1) / 3;
  }

Interestingly, the code coverage in DayDate has decreased to 84.9 percent! This is not because less functionality is being tested; rather it is because the class has shrunk so much that the few uncovered lines have a greater weight. DayDate now has 45 out of 53 executable statements covered by tests. The uncovered lines are so trivial that they weren't worth testing.

Key Ideas

  • Small refactorings compound into large improvements.
  • Replace sets of related int constants with enums — easier to rename and change.
  • Remove dead code and obsolete comments; move implementation details into derivatives.
  • Use the Abstract Factory pattern when a base class needs information about its derivatives.
  • Test coverage enables bold refactoring — but coverage can drop when the class shrinks.

Try It Yourself

  1. Replace a set of related int constants with an enum.
  2. Find a class that is a "base" but knows about its derivatives — invert the dependency with a factory.
  3. Delete a feature flag that has been "on" for more than a year.

Smells and Heuristics

A knowledge base for the practising craftsman

Martin Fowler identified many different "Code Smells." The list that follows includes many of Martin's smells and adds many more of my own. It also includes other pearls and heuristics that I use to practise my trade. I compiled this list by walking through several different programs and refactoring them. As I made each change, I asked myself why I made that change and then wrote the reason down here. The result is a rather long list of things that smell bad to me when I read code.

Comments (C1–C5): inappropriate information (change histories, authors), obsolete comments, redundant comments, poorly written comments, commented-out code. When you see commented-out code, delete it — your source control still remembers it.

Environment (E1–E2): building a project should be a single trivial operation. Running all the unit tests should be a single trivial operation.

Functions (F1–F4): too many arguments, output arguments, flag arguments, dead functions. More than three arguments is very questionable and should be avoided with prejudice.

General (G1–G36): multiple languages in one source file; obvious behaviour unimplemented; incorrect behaviour at the boundaries; overridden safeties; duplication; code at the wrong level of abstraction; base classes depending on their derivatives; too much information; dead code; vertical separation; inconsistency; clutter; artificial coupling; feature envy; selector arguments; obscured intent; misplaced responsibility; inappropriate static; use explanatory variables; function names should say what they do; understand the algorithm; make logical dependencies physical; prefer polymorphism to if/else or switch/case; follow standard conventions; replace magic numbers with named constants; be precise; structure over convention; encapsulate conditionals; avoid negative conditionals; functions should do one thing; hidden temporal couplings; don't be arbitrary; encapsulate boundary conditions; functions should descend only one level of abstraction; keep configurable data at high levels; avoid transitive navigation.

Java (J1–J3): avoid long import lists by using wildcards; don't inherit constants; constants versus enums — use enums.

Names (N1–N7): choose descriptive names; choose names at the appropriate level of abstraction; use standard nomenclature where possible; unambiguous names; use long names for long scopes; avoid encodings; names should describe side effects.

Tests (T1–T9): insufficient tests; use a coverage tool; don't skip trivial tests; an ignored test is a question about an ambiguity; test boundary conditions; exhaustively test near bugs; patterns of failure are revealing; test coverage patterns can be revealing; tests should be fast.

This list is meant to be read from top to bottom and also to be used as a reference. There is a cross-reference for each heuristic that shows where it is referenced in the rest of the text. Clean code is not written by following a set of rules. You don't become a software craftsman by learning a list of heuristics. Professionalism and craftsmanship come from values that drive disciplines.

// G5: Duplication
int size() { /* ... */ }
boolean isEmpty() { return 0 == size(); }

// G25: Replace magic numbers with named constants
double milesWalked = feetWalked / 5280.0;   // magic
double milesWalked = feetWalked / FEET_PER_MILE;   // named

// G29: Avoid negative conditionals
if (!buffer.shouldNotCompact()) { /* ... */ }   // negative
if (buffer.shouldCompact())   { /* ... */ }   // positive

// G36: Avoid transitive navigation
myCollaborator.doSomething();   // good
a.getB().getC().doSomething();  // train wreck

Key Ideas

  • Comments (C1–C5): inappropriate, obsolete, redundant, poorly written, commented-out.
  • Functions (F1–F4): too many arguments, output arguments, flag arguments, dead functions.
  • General (G1–G36): duplication, wrong level of abstraction, dead code, magic numbers, feature envy.
  • Names (N1–N7): descriptive, appropriate level, unambiguous, no encodings, describe side effects.
  • Tests (T1–T9): sufficient, fast, independent, on boundaries, near bugs.
  • Heuristics are prompts to think — not rules to follow blindly.

Try It Yourself

  1. Walk through one source file and mark every smell you find.
  2. Fix the top three smells.
  3. Write a heuristic of your own — a rule you apply when writing code — and add it to the list.

Appendix

Glossary of Useful Terms

A quick reference for the practising craftsman

Key Terms

Active Record
A DTO with navigational methods like save and find; treat it as a data structure, and keep business rules in separate objects.
Args
The command-line argument parser from the successive refinement case study; uses the Marshaler pattern.
ArgumentMarshaler
An object that knows how to parse and hold one kind of argument (boolean, string, integer, double).
AOP (Aspect-Oriented Programming)
A general-purpose approach to restoring modularity for cross-cutting concerns by specifying aspects.
BOY SCOUT RULE
Leave the campground cleaner than you found it; leave each module a little cleaner than you found it.
ComparisonCompactor
The JUnit module that exposes string comparison differences; the subject of Chapter 15.
Cross-cutting concern
A concern (persistence, security, transactions) that cuts across the object boundaries of a domain.
Dependency Injection (DI)
Inversion of Control applied to dependency management; an object's dependencies are provided by an external mechanism.
DIP (Dependency Inversion Principle)
Depend upon abstractions, not on concrete details.
DRY (Don't Repeat Yourself)
Every piece of knowledge must have a single, unambiguous representation in the system.
DTO (Data Transfer Object)
A class with public variables and no functions; a pure data structure.
Emergent design
Good design that emerges from following four simple rules: runs all tests, no duplication, expresses intent, minimises classes and methods.
F.I.R.S.T.
Fast, Independent, Repeatable, Self-Validating, Timely — the five rules of clean tests.
Heuristic
A rule of thumb, a prompt to think, not a hard rule.
Law of Demeter
A module should not know about the innards of the objects it manipulates; talk to friends, not strangers.
Learning test
A test written to learn a third-party API; it focuses on what you want out of the API.
Marshaler pattern
A pattern that pushes argument-type behaviour into polymorphic derivatives, replacing type-switches.
OCP (Open-Closed Principle)
Classes should be open for extension but closed for modification.
POJO (Plain-Old Java Object)
An object with no framework dependencies; the domain logic of an application.
Refactoring
Improving the design of existing code without changing its behaviour.
SerialDate
A date class from JCommon that represents a day without a time; the subject of Chapter 16.
Smell
A surface indication that usually corresponds to a deeper problem in the code.
SRP (Single Responsibility Principle)
A class or module should have one, and only one, reason to change.
TDD (Test Driven Development)
A discipline in which tests are written before the production code, in a thirty-second cycle.
Test Double
A stand-in for a real object used in testing; mocks and stubs are examples.
Train wreck
A chain of method calls like a.getB().getC().doSomething(); a Law of Demeter violation.
Unchecked exception
An exception that does not need to be declared in a method signature; preferred over checked exceptions for application development.
YAGNI (You Aren't Gonna Need It)
Don't build what you don't need; implement only today's stories.
